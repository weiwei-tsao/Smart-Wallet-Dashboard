很好，接下来我们深入细化后端（BFF）服务的设计。

## 2. 后端（Node/Express BFF）

这个 **BFF (Backend for Frontend)** 层是整个项目的枢纽，它的主要作用是整合来自不同数据源（链上 API、数据库）的数据，并以统一、高效的格式提供给前端。这不仅能简化前端的数据请求逻辑，还能集中管理缓存和业务逻辑，从而提升性能。

### **2.1 REST API 接口设计**

我们将为每个主要功能设计清晰、符合 RESTful 规范的 API 路由。

- **交易数据接口**

  - **路由**：`GET /api/txs?address=<wallet_address>`
  - **参数**：
    - `address` (必需)：要查询的钱包地址。
    - `page` (可选)：分页页码，例如 `page=1`。
    - `limit` (可选)：每页条目数，例如 `limit=20`。
  - **功能**：这个接口是 BFF 的核心。它会调用 Etherscan 或类似的链上数据 API 来获取一个地址的交易列表。为了减少前端的请求负担，BFF 在这里会进行一次**数据精简和格式化**。它只会返回前端需要的关键信息，例如：`hash`, `from`, `to`, `value`, `timestamp`。
  - **注意**：我们将在这里集成 Redis 缓存，以减少对外部 API 的重复请求。

- **ERC-20 Token 列表接口**

  - **路由**：`GET /api/tokens?address=<wallet_address>`
  - **参数**：
    - `address` (必需)：要查询的钱包地址。
  - **功能**：调用链上数据 API 获取某个地址所持有的所有 ERC-20 Token 列表。BFF 层会处理好每个 Token 的名称、符号、合约地址和余额，然后以简洁的 JSON 格式返回。

- **收藏地址 CRUD 接口**
  - **功能**：这些接口将与 PostgreSQL 数据库交互，用于存储和管理用户的收藏地址。
  - **新增收藏**：`POST /api/favorites`
    - **请求体**：`{ "address": "0x...", "alias": "My Main Wallet" }`
    - **返回**：新增的收藏地址对象。
  - **获取收藏列表**：`GET /api/favorites`
    - **功能**：返回用户所有收藏地址的列表。
  - **删除收藏**：`DELETE /api/favorites/:id`
    - **参数**：`id` (必需)：数据库中收藏地址的 ID。
    - **返回**：操作成功或失败的提示。

### **2.2 技术栈与实现细节**

- **Node.js 框架**：使用 **Express.js** 框架来快速搭建 RESTful API。
- **缓存层 (Redis)**：
  - **集成**：使用 `redis` 客户端库。
  - **缓存策略**：在处理 `/api/txs` 和 `/api/tokens` 请求时，首先检查 Redis 缓存中是否有该地址的数据。
  - **键名**：使用清晰的键名，例如 `cache:txs:<address>` 或 `cache:tokens:<address>`。
  - **过期时间 (TTL)**：设置 30-60 秒的过期时间。这既能保证数据的相对新鲜度，又能显著降低对外部 API 的请求频率。
- **数据存储 (PostgreSQL)**：

  - **集成**：使用 **Prisma** 或 **Sequelize** 等 ORM 工具来连接和操作 PostgreSQL 数据库。
  - **表结构**：设计一个 `favorites` 表，包含以下字段：
    - `id` (主键, UUID)
    - `address` (字符串, 唯一索引, 钱包地址)
    - `alias` (字符串, 昵称)
    - `createdAt` (时间戳)
    - `updatedAt` (时间戳)

- **代码组织**：
  - 将路由、控制器、服务层和缓存逻辑分开，遵循分层架构原则。
  - 例如，可以有一个 `routes/` 目录存放 API 路由文件，一个 `controllers/` 目录处理请求逻辑，以及一个 `services/` 目录封装与外部 API 和数据库的交互。

---

BFF 层的核心在于其**数据聚合和缓存**能力，它将作为前端和复杂数据源之间的坚固屏障。
