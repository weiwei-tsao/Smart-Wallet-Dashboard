## 3. 基础设施（Docker & CI/CD）

### 3.1 Docker & Docker Compose

我们将使用 **Docker Compose** 来定义和运行整个应用栈。它允许你用一个简单的配置文件启动所有服务，包括前端、后端、缓存和数据库，从而保证开发环境的一致性和可移植性。

- **`docker-compose.yml` 文件**

  - 在项目根目录下创建这个文件。它将定义四个核心服务：`web`、`bff`、`redis` 和 `postgres`。
  - **`web` 服务 (Next.js)**：
    - 使用一个轻量级的 Node.js 镜像，例如 `node:18-alpine`。
    - 在 `Dockerfile` 中，我们将安装依赖、构建项目，并以 `CMD ["npm", "run", "dev"]` 运行开发服务器。
    - **端口映射**：将容器的 3000 端口映射到宿主机的 3000 端口，让你可以通过 `http://localhost:3000` 访问前端。
    - **卷 (Volumes)**：挂载本地代码目录，实现热重载，方便开发。
  - **`bff` 服务 (Node/Express)**：
    - 使用与 `web` 服务相同的 Node.js 镜像。
    - 同样的，在 `Dockerfile` 中安装依赖，并用 `CMD ["npm", "run", "dev"]` 运行 Express 服务。
    - **端口映射**：将容器的 3001 端口映射到宿主机的 3001 端口。
  - **`redis` 服务**：
    - 使用官方的 `redis` 镜像。
    - **端口映射**：可选，如果不暴露端口，`bff` 服务可以直接通过 Docker 内部网络访问。
  - **`postgres` 服务**：
    - 使用官方的 `postgres` 镜像。
    - **环境变量**：设置数据库名称、用户名和密码等环境变量，例如 `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`。这些变量需要与 `bff` 服务中的数据库连接字符串保持一致。

- **README 指南**
  - 在项目的 `README.md` 中，提供清晰的**一键启动**命令，例如：`docker-compose up --build`。
  - 解释每个服务的用途以及如何访问它们（例如，前端在 `localhost:3000`，后端在 `localhost:3001`）。

### 3.2 GitHub Actions CI/CD

**持续集成（CI）** 流程确保每次代码提交或拉取请求（PR）都经过自动化测试和检查，从而在早期发现问题。

- **`.github/workflows/ci.yml` 配置文件**

  - 创建此 YAML 文件来定义 CI 流程。
  - **触发条件**：将工作流配置为在每次 `push` 到 `main` 分支或创建 `pull request` 时自动运行。
  - **CI 步骤**：
    1.  **安装依赖**：运行 `npm ci` 来安装项目依赖。使用 `ci` 而不是 `install` 可以确保版本锁死，避免不一致性。
    2.  **Linting (代码风格检查)**：运行 `npm run lint`。这有助于强制执行一致的代码风格，避免低级错误。
    3.  **Type-checking (类型检查)**：对于 TypeScript 项目，运行 `npm run type-check`。这是确保代码类型安全的关键一步。
    4.  **Unit Tests (单元测试)**：运行 `npm test`。这是验证业务逻辑是否按预期工作的核心环节。
    5.  **Build (构建)**：运行 `npm run build` 来检查项目是否可以成功构建，这是部署前的最后一道关卡。

- **可选的持续部署（CD）**
  - **自动部署**：可以为 GitHub Actions 添加一个部署步骤，当代码成功合并到 `main` 分支后，自动将前端部署到 **Vercel**（对于 Next.js 项目非常方便）或将后端部署到 **Render** 等云服务商。
  - **部署脚本**：在工作流中添加一个 `deploy` 步骤，使用云服务商提供的 CLI 工具或 GitHub Actions 市场中的相应 Action 来触发部署。
