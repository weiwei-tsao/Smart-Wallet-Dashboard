## 📊 版本管理最佳实践

### **分支命名规范**

- `feature/功能名称` - 新功能开发
- `hotfix/修复描述` - 紧急修复
- `release/版本号` - 发布准备
- `milestone/里程碑描述` - 重要里程碑

### **提交信息规范**

```bash
# V1.0 维护
git commit -m "fix(v1.0): 修复钱包连接问题"
git commit -m "hotfix: 紧急修复安全漏洞"

# V2.0 开发
git commit -m "feat(v2.0): 实现 Next.js 迁移"
git commit -m "feat(v2.0): 添加后端 BFF 服务"
git commit -m "feat(v2.0): 集成 Docker 容器化"
```

### **标签管理策略**

- **版本标签**：`v1.0.0`, `v2.0.0` - 正式发布版本
- **里程碑标签**：`milestone/描述` - 重要开发节点
- **预发布标签**：`v2.0.0-beta.1` - 测试版本

## 🔄 版本发布流程

### **V2.0 发布流程**

1. **功能开发完成**

   ```bash
   git checkout develop
   git checkout -b feature/new-feature
   # ... 开发 ...
   git checkout develop
   git merge feature/new-feature
   ```

2. **创建发布分支**

   ```bash
   git checkout develop
   git checkout -b release/v2.0.0
   # ... 测试和修复 ...
   ```

3. **发布到生产**

   ```bash
   git checkout main
   git merge release/v2.0.0
   git tag -a v2.0.0 -m "V2.0 - Next.js + BFF + Docker"
   git push origin main --tags
   ```

4. **合并回开发分支**
   ```bash
   git checkout develop
   git merge release/v2.0.0
   ```

## 📈 版本管理优势

✅ **版本隔离**：V1.0 和 V2.0 完全分离，互不影响
✅ **稳定维护**：V1.0 可以继续维护和修复
✅ **并行开发**：V2.0 可以独立开发新功能
✅ **清晰历史**：每个版本都有清晰的提交历史
✅ **灵活发布**：可以独立发布 V1.0 和 V2.0 的更新
✅ **风险控制**：V2.0 开发不影响 V1.0 的稳定性
